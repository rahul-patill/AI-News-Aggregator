# Services Documentation

The `services` folder contains the core "business logic" pipelines for the application. While the scrapers just fetch raw data and the repository just saves it, the services are responsible for taking that raw data, processing it (getting missing information, generating AI summaries), and ultimately delivering it to the user.

Most of these files act as independent "jobs" that look through the database for unfinished work, complete that work, and save the results back.

---

## File Breakdown

### 1. `process_anthropic.py`
**Goal: Fetch Full Article Text**
When the Anthropic scraper first finds an article via the RSS feed, it often only gets a short description. This service looks in the database for any Anthropic articles that are missing their full `markdown` content. It then visits the actual webpage, converts the page into Markdown format, and updates the database row with the full article text.

### 2. `process_youtube.py`
**Goal: Fetch Video Transcripts**
Similar to Anthropic, the YouTube scraper initially just gets video titles and URLs from RSS feeds. This service queries the database for any YouTube videos that don't have a transcript yet. It connects to the YouTube API, downloads the full captions/transcript for the video, and updates the database. If a video doesn't have a transcript available, it marks it as `__UNAVAILABLE__` so it doesn't try again next time.

### 3. `process_digest.py`
**Goal: Generate AI Summaries**
Once we have the full text (from Anthropic markdown or YouTube transcripts), this service takes over. It looks for any raw articles or videos that haven't been summarized yet. It passes the massive raw text into the **DigestAgent** (an AI model), which reads it and generates a concise, readable summary (a `Digest`). It then saves this new Digest into the database.

### 4. `process_curator.py`
**Goal: Rank Articles for the User**
We don't want to spam the user with 50 articles. This service grabs all the AI Digests from the last 24 hours and passes them to the **CuratorAgent**. The Curator Agent looks at the `USER_PROFILE` (who the user is, their background, their interests) and gives each digest a relevance score from 0-10, ranking them from most interesting to least interesting specifically for that user.

### 5. `process_email.py`
**Goal: Generate the Final Newsletter**
This service orchestrates the final step. It takes the top-ranked articles generated by the Curator, passes them to the **EmailAgent** to write a personalized introduction/greeting, formats everything into a clean Email structure, and then triggers the actual sending process.

### 6. `email.py`
**Goal: Send the Email**
This is a utility file. It contains the raw logic for connecting to the Gmail SMTP server using your `MY_EMAIL` and `APP_PASSWORD`. It takes the Markdown email generated by `process_email.py`, converts it into beautiful HTML (using custom CSS for styling), and fires it off to your inbox.

## How Data is Extracted

A common question is how we actually get the deep text for our AI to summarize. Here is how each source is handled:

### 1. How we get Anthropic Markdown
The Anthropic RSS feed only gives us a tiny summary of the article and a link. To get the full text, the `process_anthropic.py` service uses a special library called **Docling** (`DocumentConverter`). Docling acts like a virtual browser: it goes to the article's URL, strips away all the messy HTML, ads, and navigation bars, and returns just the pure article text perfectly formatted as Markdown. 

### 2. Why there is no Markdown for OpenAI
Unlike Anthropic, OpenAI is very generous with their RSS feed. Instead of just giving us a tiny summary, OpenAI's RSS feed actually embeds the **entire full-text article** directly inside the `<description>` tag of the feed itself. Because we already get the full text automatically during the initial scraping phase, we don't need a separate service to visit their website and generate Markdown.

### 3. How we get YouTube Transcripts
YouTube videos obviously don't have "articles" to read. Instead, the `process_youtube.py` service leverages an unofficial API wrapper called `youtube_transcript_api`. When we pass a video ID to this library, it reaches into YouTube's backend and downloads the hidden Closed Captions (either auto-generated by Google or manually uploaded by the creator). This gives our AI a massive block of text containing everything that was spoken in the video!

## Core Processing Logic (How it works under the hood)

Across all of these services, we use a very specific design pattern to make sure the app runs smoothly, fast, and doesn't waste API calls. The logic is based on **Idempotency and State Checking**:

1. **State Checking (Querying for 'Nulls')**
   Instead of looping through *all* articles every time the script runs, the services ask the database a specific question: *"Give me only the rows where the work isn't done yet."* 
   For example, `process_youtube.py` asks for rows where `transcript IS NULL`. `process_digest.py` asks for articles that don't have a matching row in the `digests` table.

2. **Error Handling & Blacklisting**
   If a service tries to process something and it fails (e.g., a YouTube video doesn't have closed captions enabled), the app doesn't just leave it as `NULL` (otherwise it would try and fail again tomorrow, wasting time). Instead, it updates the database with a specific marker like `__UNAVAILABLE__`. The next time the script asks for unfinished work, it sees `__UNAVAILABLE__` and knows to safely skip it.

3. **Batch Committing**
   As the scripts run through their loops, they process items one by one, but they constantly update the database state (`self.session.commit()`). If the script suddenly crashes halfway through, no work is lost. The next time you run it, it picks up exactly where it left off because the database state is always accurate.
